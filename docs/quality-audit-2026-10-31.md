# 电脑百宝箱 · 代码与体验检测报告

- 检测对象：`FileKeeper`（版本 `2.2.1`）
- 检测日期：2026-10-31
- 检测范围：启动/单实例、配置、备份引擎、任务调度、定时关机、时间闹钟、计时器、快速截图、全局热键、截图保存、托盘、设置、来源选择器、安装/卸载
- 检测方式：逐模块代码审阅 + 关键路径推演 + 现有测试回归 + 针对配置损坏、计时器配置等做了可复现验证
- 说明：本报告只给修改建议，不修改现有源码；P0 破坏性操作未在本机实际执行（避免真的删备份/关机）
- **后续状态**：2026-10-31 已按本报告修复（QA-28 按要求不改，QA-10/16/18/25 按用户定制行为实现），见 [fix-report-2026-10-31.md](fix-report-2026-10-31.md)

## 一、总体结论

软件整体结构清晰，便携式配置、单实例、隐藏托盘、自绘 UI、无第三方运行时依赖这些方向都做得不错；截图保存的原子替换、保存防重入、隐藏项选择器也有较完整的边界处理。

但当前版本有几个**会造成数据丢失或误操作**的高风险点，主要集中在：

1. **镜像备份的“清理多余文件”**：来源扫描不完整时，可能把备份目标中仍然有效的文件删掉。
2. **卸载程序**：如果用户把软件装进一个已有其他文件的目录，选择“全部删除”会删除整个安装目录。
3. **托盘快捷关机**：没有二次确认，误点即安排关机。
4. **还原备份**：同名文件直接覆盖，没有覆盖清单和确认，也没有接入取消。
5. **配置损坏**：JSON 语法正确但字段类型错误时，会在启动阶段直接抛异常；配置写盘失败又被静默吞掉。

因此，**不建议在未修复 P0 项之前用于无人值守/重要资料备份**。普通个人使用也建议优先修复 P0/P1。

## 三、详细问题与修改建议

### QA-01（严重）镜像清理可能误删有效备份

**位置**

- `fk/backup.py:156-192`：`iter_tree()` 使用 `os.walk(..., onerror=lambda err: None)`，读取失败的目录被静默跳过；单个文件 `stat()` 失败时还会以 `size=0` 继续产出。
- `fk/backup.py:474-489`：镜像清理用本次扫描得到的 `files` 构造 `source_set`，目标中“不在集合内”的文件直接 `os.remove()`。

**现象/触发条件**

- 来源目录中某个子目录临时无权限、被其他程序锁定、网络共享断开，或扫描过程中出现 I/O 错误；
- 该子目录没有进入 `files`；
- 清理阶段把目标中该子目录对应的旧备份判为“多余”，删除。

**影响**

这是最严重的一类问题：一次不完整的来源扫描，可能把上一次完好的备份删掉。用户通常只有在需要还原时才发现。

**修改建议**

1. `iter_tree()` 不要静默忽略错误：收集 `scan_errors`，或者让生成器抛出 `BackupScanError`。
2. 镜像清理增加前置条件：只有“扫描完整、所有来源可访问、复制阶段没有严重错误”时才允许 `delete_extraneous`。
3. 删除前先生成待删清单，写入日志/UI 摘要；可增加“仅预览不删除”或二次确认。
4. 如果来源根目录不可访问、或扫描结果为 0（原本非空），一律禁止清理。
5. 测试用例：模拟子目录权限错误、网络中断、文件在扫描后消失，断言目标文件不被删除。

**建议优先级**：立即修复，修复前可先默认关闭 `delete_extraneous`。

### QA-02（严重）卸载会删除整个安装目录

**位置**：`installer/uninstall.bat:30-39`

**现象**

用户选择“全部删除”后执行：

```bat
rmdir /s /q "%DEST%"
```

而 `DEST` 是安装程序所在目录。安装时用户可以自由选择已存在的目录（例如 `D:\Tools`、项目目录、甚至某个资料目录），因此卸载会连同目录中与软件无关的文件一起删除。

**影响**

不可恢复的数据丢失；如果安装到根目录或共享目录，影响更大。

**修改建议**

1. 安装时强制使用专用子目录 `...\电脑百宝箱`，禁止直接把任意已有目录作为安装根目录。
2. 卸载只删除已知文件（exe、uninstall.bat、install_log.txt）和专用 `data` 子目录，不要对父目录 `rmdir /s /q`。
3. “全部删除”前列出将删除的路径和大小，要求再次确认。
4. 对根目录、系统目录、用户资料目录做黑名单保护。

### QA-03（严重）托盘快捷关机没有确认

**位置**

- `fk/ui/app.py:1173-1180`：托盘菜单调用 `page.quick(source, confirm=False)`。
- `fk/ui/shutdown.py:387-399`：`quick()` 直接把 `confirm` 传给 `_arm()`，`confirm=False` 时立即调用 `shutdown.arm()`。

**现象**

托盘菜单中的“明天 08:00 关机 / 今天 08:00 关机 / 10 小时后关机”单击即生效，没有“确定要关机吗”的确认。托盘菜单本身又比较容易被误点。

**影响**

误操作导致计算机在预期之外关机，可能丢失未保存工作。

**修改建议**

1. 所有关机动作统一走确认对话框，至少显示目标时间和“关机前请保存文件”。
2. 托盘里可以保留快捷入口，但点击后弹出小型确认；或改成二次点击/长按确认。
3. 已经有关机计划时，新增计划前提示“将替换现有计划”。

### QA-04（高）还原直接覆盖同名文件，无确认、无取消

**位置**

- `fk/ui/tasks.py:344-374`：选择快照和还原目标后直接 `_do_restore()`。
- `fk/backup.py:624-701`：`shutil.copy2()` 直接写目标，同名文件被覆盖；虽然函数支持 `cancel`，UI 没有传入取消事件。

**现象**

- 用户选择还原到桌面、文档目录或某个已有目录时，同名文件无提示被覆盖；
- 还原过程中没有进度/取消入口；
- 无法选择“跳过已存在文件”或“先备份目标文件”。

**影响**

误覆盖用户当前文件；还原一半时无法停止。

**修改建议**

1. 还原前预扫描：显示文件数、总大小、冲突文件数、将被覆盖的示例路径。
2. 提供“覆盖 / 跳过同名 / 取消”三种策略；默认建议“跳过”或“先备份”。
3. 将 `cancel` 事件接入 UI，还原页显示进度和取消按钮。
4. 还原完成后给出“复制/跳过/失败”汇总。
5. 若目标在备份目录内部，明确拒绝。

### QA-05（高）任务目标目录可重复或嵌套

**位置**

- `fk/ui/tasks.py:1073-1095`：`_validate()` 只检查“来源 vs 本任务目标”，没有检查其他任务目标。
- `fk/config.py:415-432`：`add_task/update_task` 没有唯一性校验。

**现象**

- 两个任务可以配置相同 `target`；
- 一个任务目标可以是另一个任务目标的子目录/父目录；
- 任务名重复时，从主备份目录派生出的目标也会重复。

**影响**

镜像清理、快照清理、日志写入会互相干扰；一个任务可能删除另一个任务的备份内容。

**修改建议**

1. 保存任务时对全部任务做目标关系检查：相等、父子目录都拒绝或要求明确确认。
2. 任务名重复时自动追加 `(2)`，或禁止重复。
3. 对“目标已存在且非空”的首次配置提示用户。
4. 增加回归测试：两个任务同目标、父子目标、同名任务。

### QA-06（高）备份执行器存在并发竞态

**位置**：`fk/runner.py:26-43`、`64-84`

**代码要点**

```python
with self._lock:
    ...
    should_start = self._thread is None and bool(self._pending)
if should_start:
    self._thread = threading.Thread(...)
    self._thread.start()
```

`should_start` 在锁内计算，但 `self._thread` 的赋值在锁外。两个线程（例如调度线程和 UI 线程）同时 `enqueue()` 时，都可能看到 `_thread is None`，各自启动一个工作线程。

**影响**

备份任务不再串行；两个 `run_backup()` 同时修改同一配置/目标目录，UI 事件也会交错，最坏情况是目标文件互相覆盖或清理。

**修改建议**

1. 把线程创建和 `_thread` 赋值放进同一把锁；或增加 `_starting` 标志。
2. 更稳妥：用一个常驻 worker + `queue.Queue`，不要每次 enqueue 创建线程。
3. 用并发测试（两个线程同时 enqueue）验证只创建一个 worker。

### QA-07（高）合法 JSON 但字段类型错误会导致启动崩溃

**位置**

- `fk/config.py:41-80`（`Schedule.from_dict`）
- `fk/config.py:119-160`（`Task.from_dict`）
- `fk/config.py:213-271`（`Settings/HistoryEntry.from_dict`）
- `fk/config.py:311-371`（`Config.load`）

**已复现**

把 `config.json` 写成合法 JSON，但让数值字段为字符串：

```json
{"settings": {"keep_versions": "abc"}}
{"tasks": [{"id":"t1","name":"x","keep_versions":"abc"}]}
{"tasks": [{"id":"t1","name":"x","schedule":{"interval_min":"abc"}}]}
{"history": [{"id":"h1","copied":"abc"}]}
```

四种情况都会在 `Config.load()` 抛：

```text
ValueError: invalid literal for int() with base 10: 'abc'
```

`Config.load` 只捕获 JSON 解析错误和 OSError，不捕获模型转换异常，因此启动直接失败。

**影响**

手工编辑配置、旧版本字段、同步工具写坏、第三方修改后，软件无法启动。

**修改建议**

1. 为 `int/float/bool/list` 字段增加安全转换函数，失败时使用默认值并记录 warning。
2. `Config.load` 对 `settings/tasks/history/alarm/timers` 逐段 try/except，坏数据降级而不是整体崩溃。
3. 启动时把损坏文件另存为 `config.json.bad-时间戳`，不要直接覆盖。
4. 增加“字段类型损坏”测试，覆盖 settings/task/schedule/history/timers。

### QA-08（高）配置保存失败被静默吞掉

**位置**：`fk/config.py:379-405`

`save()` 内部捕获 `OSError` 后只删除临时文件，不抛出、不返回失败；`settings._save()` 等调用方仍然显示“设置已保存”。

**影响**

磁盘满、目录只读、被杀毒软件锁定、权限不足时：

- 用户以为设置/任务已保存；
- 重启后恢复旧配置；
- 备份记录、闹钟、关机计划可能丢失。

**修改建议**

1. `save()` 返回 `bool` 或抛 `ConfigSaveError`。
2. 所有“保存成功”提示以实际写盘结果为准；失败时显示路径和错误。
3. 写临时文件后 `flush` + `os.fsync`，再 `os.replace`；保留上一份 `config.json.bak`。
4. 增加磁盘满/只读目录测试（可 mock）。

### QA-09（高）多来源同名覆盖与目录布局变化

**位置**

- `fk/backup.py:195-219`：只有一个文件夹来源时 `should_strip_root()` 为真，直接铺平内容；多来源时用 `source.name + "/"` 作为前缀。
- `fk/backup.py:448-457`：`shutil.copy2()` 不检查目标是否已存在，后复制者覆盖先复制者。

**现象**

- 两个不同目录都叫 `Photos`，合并到目标后互相覆盖；
- 两个单独文件同名，后一个覆盖前一个；
- 先备份一个文件夹（目标根下是 `a.jpg`），后来再加一个来源，布局变成 `Photos/a.jpg`，镜像清理会把旧的 `a.jpg` 当多余文件删除。

**影响**

静默丢文件、备份结构变化、镜像清理误删。

**修改建议**

1. 复制前建立目标相对路径集合，发现冲突时中止并报告，或自动加 `(2)`。
2. 目录布局规则固定：建议始终按“来源名/相对路径”保存，不要因来源数量变化而切换布局；若必须铺平，需显式选项并固定。
3. 在任务预览里显示实际目标结构；来源数量变化时提示用户。

### QA-10（中高）退出流程会先取消关机，再可能取消退出

**位置**：`fk/ui/app.py:1257-1285`

**流程**

1. 有关机计划 → 询问“取消并退出 / 保持并退出 / 取消退出”；
2. 选择“取消并退出” → 立即 `_cancel_shutdown_for_exit()`；
3. 接着发现备份仍在进行，询问是否退出；
4. 用户选择“不退出”；
5. 软件留下了，但关机计划已经被取消。

**影响**

用户以为只是取消退出，实际上关机计划已经丢失。

**修改建议**

先收集所有退出决策（关机计划 + 备份中），最后一步才执行副作用：

```
询问关机计划 -> 询问备份中 -> 全部确认后：
  如果需要取消关机 -> shutdown.cancel()
  然后退出
```

任何一步取消退出，都不要提前修改关机计划。

### QA-11（中）失败/取消的备份也消耗调度时间点

**位置**

- `fk/config.py:451-489`：`record_result()` 无论 `success/failed/cancelled` 都写 `target.last_run = entry.time`。
- `fk/scheduler.py:59-105`：`last_run >= target` 即认为当天已完成。

**影响**

- 网络临时中断导致失败后，每日任务不会在当天再试；
- 用户主动取消也算“已运行”，当天不再自动执行；
- 没有“上次失败，稍后重试”的机制。

**修改建议**

1. 区分 `last_attempt` 与 `last_success`；调度只以成功为准，或增加失败重试次数/退避。
2. 对 `failed` 提供“立即重试”和“当天稍后重试”策略。
3. 取消操作不应写成成功；至少 UI 显示“已取消，本次计划未完成”。

### QA-12（中）关机前无条件取消其他关机计划

**位置**：`fk/shutdown.py:46-60`

```python
_run(["/a"])  # 先清掉可能存在的旧计划
```

这会取消系统或其他程序已经安排的关机计划，而不只是本软件的旧计划；没有任何提示。

**修改建议**

1. 尽量查询当前计划；无法查询时，只有在“本软件记录了自己的计划”或用户明确同意替换时才执行 `/a`。
2. 新设计划时提示“将替换现有的系统关机计划，是否继续”。
3. 记录计划来源/时间，退出时只取消自己创建的计划。

### QA-13（中）过期闹钟在启动时被静默清除

**位置**

- `fk/ui/alarm.py:311-314`：页面构建末尾调用 `_refresh_status()`。
- `fk/ui/alarm.py:447-451`：目标时间已过时直接 `clear_alarm()`，没有任何提示。
- `fk/ui/alarm.py:493-509`：如果 `_refresh_status` 没先执行，`_tick` 又会把过期提醒当成刚到点而补响。

**现象**

- 设了 08:00 提醒，关闭软件；
- 09:00 打开软件；
- 页面构建时 `_refresh_status()` 已把提醒清掉，用户看不到“已错过”；
- 如果执行顺序不同（`_tick` 先跑），又会立刻弹一个“时间到了”的提醒。行为不一致。

**修改建议**

1. 明确“过期提醒”的产品语义：补响并标注“已过期 X 分钟”，或显示“已错过”并让用户选择重新设定/忽略。
2. 不要在加载时静默清除；保存 `missed` 状态并主动提示。
3. 统一 `_tick` 和 `_refresh_status` 的处理入口，避免两个路径竞争。

### QA-14（中）长路径遍历未使用 `long_path`

**位置**：`fk/backup.py:163-192`

`iter_tree()` 使用 `os.walk(str(root))`，而复制时使用了 `long_path()`。超过 260 字符的来源路径在遍历/stat 阶段就会失败；还原同样使用 `iter_tree`。

**修改建议**

1. 用 `os.walk(long_path(root))` 或自定义 `scandir` 递归；所有 `stat/relative_to` 统一处理 `\\?\` 前缀。
2. 目标路径也使用长路径前缀。
3. 增加 300 字符路径的复制/还原测试。

### QA-15（中）托盘提示文本从未真正更新

### QA-21（低中）隐藏状态下手动备份失败会弹 messagebox，内部日志被丢弃

**位置**

- `fk/ui/app.py:463-469`：只要 `manual` 且失败/部分成功，就 `messagebox.showwarning(parent=self)`；即使用户已把主窗口隐藏到托盘。

**影响**

- 托盘场景下突然弹出模态警告，打断当前工作；
- 真正的 traceback 只进了内存队列，用户/开发者看不到。

**修改建议**

### QA-22（低中）来源选择器路径栏的同步文件判断可能卡住 UNC

**位置**：`fk/ui/picker.py:383-389`

```python
if self.mode == "files" and os.path.isfile(long_path(text)):
```

这一步在 Tk 主线程执行；用户输入 UNC 文件路径时，`os.path.isfile` 可能因网络超时卡住，而目录扫描本身已经放到后台线程。

**修改建议**

把“路径是文件还是目录”的判断也放到后台线程，带 1–2 秒超时；超时后提示“网络路径无响应”，不要阻塞 UI。

### QA-23（低中）网络保存超时后后台线程仍可能继续写

**位置**：`fk/ui/screenshot.py:849-873`

超时分支：

```python
self._save_cancel.set()
self._release_save()
...
self._reselect_later()
```

后台 `save_png_atomic` 线程可能仍阻塞在网络 I/O；如果它之后继续执行，可能在用户已经重新选择目录后又写了一次，或在超时后悄悄产生文件。释放闸门也允许新的保存与旧线程并行。

**建议**

- 超时后不要立即释放闸门，等 worker 真正退出（或增加“强制放弃”状态）；
- worker 完成后检查 generation/token，不再写目标；
- 使用唯一临时文件，超时后清理。

### QA-24（低中）Tk 回调异常没有统一日志

**位置**：`main.py` 只捕获 `main()` 最外层异常；Tkinter 回调异常默认走 `report_callback_exception` 到 stderr，打包成 `--windowed` 后没有控制台。

**影响**

**修改建议**

在 `App` 初始化时覆盖：

```python
self.report_callback_exception = ...
```

写入 `app.log`，并在状态栏显示“操作失败，详情见日志”。

## 六、建议补充的测试

现有测试主要覆盖正常路径。建议新增：

1. **镜像安全测试**
   - 来源子目录无权限/被锁定/网络断开 → 目标文件不被删除；
   - 来源为空但目标非空 → 不清理；
   - 取消/失败期间不执行清理。
2. **任务冲突测试**
   - 两个任务同目标；
   - 一个任务目标是另一个的子目录/父目录；
   - 同名来源/同名文件。
3. **配置健壮性测试**
   - 合法 JSON + 错误字段类型（本次已手工复现 4 类崩溃）；
   - 写盘失败、只读目录、磁盘满；
   - 损坏配置留存 `.bad`。
4. **并发测试**
   - 多线程同时 `enqueue`，断言只有一个 worker；
   - 备份中取消 + 立即重新入队。
5. **还原测试**
   - 同名文件冲突、跳过/覆盖策略；
   - 中途取消；
   - 目标不可写。
6. **闹钟/调度边界**
   - 应用关闭跨过提醒时间再启动；
   - 跨午夜补跑；
   - 休眠唤醒。
7. **托盘/UI**
   - tooltip 变化；
   - 隐藏主窗口时备份失败只发托盘通知；
   - Tk 回调异常写入 app.log。

## 七、结论

软件的“功能完整度”已经比较高，真正需要优先解决的是**破坏性操作的安全边界**和**失败状态的可恢复性**：镜像清理、卸载、还原、配置保存这四条链路，任何一条出错都可能造成用户数据不可逆损失。

建议先把 P0/P1 做成一个“安全版本”，再继续做截图/托盘/动效类体验优化；这样比继续加功能更能提升这个工具的可靠性。
